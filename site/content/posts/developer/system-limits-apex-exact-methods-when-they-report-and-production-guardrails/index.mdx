# System.Limits Apex: exact methods, when they report, and production guardrails

Short answer

System.Limits Apex is the runtime API you use to inspect current and maximum per-transaction limits. Call the paired getters (getX and getLimitX) to measure usage and thresholds, then fail fast when remaining budget is insufficient for the work you intend to do. The examples below list the useful methods, show sync vs async behavior, include a tiny guardrail library you can drop into production, and a unit-test pattern that asserts guard behavior.

## What is System.Limits and which methods are most useful?

System.Limits exposes two kinds of methods: usage getters (e.g., Limits.getDmlRows()) and limit getters (e.g., Limits.getLimitDmlRows()). Use the pair to compute remaining budget. The methods you will use most often:

- Limits.getDmlRows() / Limits.getLimitDmlRows()
- Limits.getDmlStatements() / Limits.getLimitDmlStatements()
- Limits.getQueries() / Limits.getLimitQueries()
- Limits.getQueryRows() / Limits.getLimitQueryRows()
- Limits.getCpuTime() / Limits.getLimitCpuTime()
- Limits.getHeapSize() / Limits.getLimitHeapSize()
- Limits.getCallouts() / Limits.getLimitCallouts()
- Limits.getFutureCalls() / Limits.getLimitFutureCalls()
- Limits.getOpenCursors() / Limits.getLimitOpenCursors()
- Limits.getEmailInvocations() / Limits.getLimitEmailInvocations()
- Limits.getStreamingApiConcurrentClients() / Limits.getLimitStreamingApiConcurrentClients()

For the full canonical list and up-to-date numeric caps, see the Salesforce docs: [Apex Governor Limits | Salesforce Developer Docs](https://developer.salesforce.com/docs).

## How do reported values change in synchronous vs asynchronous contexts?

Limits are per-transaction and many caps differ between sync and async contexts. You should not hard-code a number unless you cite the docs, but patterns are predictable:

- getLimitCpuTime() returns a smaller cap for synchronous transactions and a larger one for async (batch/future/queueable). For example, CPU time limits are typically measured in milliseconds and are stricter for sync requests.
- getLimitHeapSize() similarly differs for sync vs async transactions.
- Some limits (like total query rows processed) stay the same in both contexts; others (like CPU and heap) increase for async.

Always inspect Limits.getLimitX() at runtime when you design behavior that depends on a numeric cap.

## How to fail fast in bulk jobs (small guardrail library)

Fail-fast means detect insufficient remaining budget before starting work and throw a clear exception so the transaction quickly rolls back. Drop this small utility class into your org and call it early in trigger handlers or Batchable.execute.

```apex
public class LimitsGuard {
    public class LimitException extends Exception {}

    public static void failIfLessThanDmlRows(Integer minRowsRequired) {
        Integer remaining = Limits.getLimitDmlRows() - Limits.getDmlRows();
        if (remaining < minRowsRequired) {
            throw new LimitException('Insufficient DML rows remaining: ' + remaining +
                '. Required: ' + minRowsRequired);
        }
    }

    public static void failIfLessThanHeap(Integer bytesRequired) {
        Integer remaining = Limits.getLimitHeapSize() - Limits.getHeapSize();
        if (remaining < bytesRequired) {
            throw new LimitException('Insufficient heap remaining: ' + remaining + ' bytes');
        }
    }

    public static void failIfLessThanCpu(Integer msRequired) {
        Integer remaining = Limits.getLimitCpuTime() - Limits.getCpuTime();
        if (remaining < msRequired) {
            throw new LimitException('Insufficient CPU time remaining: ' + remaining + ' ms');
        }
    }
}
```

Example usage in a Batchable.execute:

```apex
public void execute(Database.BatchableContext bc, List<sObject> scope) {
    // Estimate 1 DML row per updated child + margin
    LimitsGuard.failIfLessThanDmlRows(scope.size() + 10);
    // proceed with bulk-safe processing
}
```

Call the guards before entering expensive loops or before building large collections.

## How to write unit tests that assert limit behavior

You cannot directly increase or decrease platform limits, but you can assert that your guard logic throws when you intentionally request more than the current remaining budget.

```apex
@isTest
private class LimitsGuardTest {
    @isTest static void testFailIfLessThanDmlRows_throws() {
        Integer limit = Limits.getLimitDmlRows();
        Test.startTest();
        try {
            // request more than total allowed -> should throw
            LimitsGuard.failIfLessThanDmlRows(limit + 1);
            System.assert(false, 'Expected LimitException');
        } catch (LimitsGuard.LimitException e) {
            System.assert(e.getMessage().contains('Insufficient DML rows'));
        }
        Test.stopTest();
    }
}
```

This pattern is reliable because you use runtime values (Limits.getLimitDmlRows()) to calculate a buffer that you know will exceed remaining.

## Decision table: when to check vs trust Limits.getLimitX()

| Situation | Action | Why |
|---|---:|---|
| Small trigger (<= 10 records), only read/update one field | Trust | Low per-transaction cost; additional checks add overhead |
| Bulk processing (100s–thousands via Batchable/Queueable) | Check before heavy work | Protects against partial progress and wasted API calls |
| Calling external services or doing nested DML | Check CPU and heap | External callouts + joins can spike CPU/heap quickly |
| Long-running aggregate computation | Check CPU and fail early to reschedule async | Async has higher CPU, but rescheduling is safer than timeout |

## Common mistakes (and how to fix them)

- **Assuming sync and async caps are identical.** Fix: call Limits.getLimitX() at runtime and branch if you need different behavior.
- **Doing SOQL/DML inside a loop.** Fix: bulkify — collect Ids, query once, then process lists before doing one DML.
- **Building giant lists before checking heap.** Fix: check Limits.getHeapSize() and stream-processing patterns (process in chunks, call update every N records).
- **Trusting unit test coverage to catch limit issues.** Fix: write tests that assert guard behavior and add integration tests that run with realistic dataset sizes.
- **Ignoring estimated per-record cost.** Fix: in Batch.execute, compute a conservative per-record budget and call a guard early (see guard example above).

## FAQ

### Where can I find the exact numeric governor limits referenced by System.Limits?

See the official documentation: [Apex Governor Limits | Salesforce Developer Docs](https://developer.salesforce.com/docs). The docs list current numeric caps and which limits differ for sync vs async.

### Does Limits.getCpuTime() measure wall-clock time or CPU time?

It reports CPU time used by the transaction (milliseconds). Use Limits.getLimitCpuTime() to know the allowed cap for the current transaction type.

### Can I rely on Limits.getLimitX() returning the same value across all orgs?

No. Some limits can differ by edition or feature. Always read Limits.getLimitX() at runtime before making decisions that depend on exact numeric caps.

### What’s the best place to call a guard in a trigger framework?

Call guards at the start of your trigger handler, before expensive operations (especially before any callouts or large DML). For batch jobs, call guards at the start of execute() for each scope.

### Will using the guard library add meaningful overhead?

The checks are constant-time integer calculations calling lightweight getters. The overhead is negligible compared with the cost of the operations they prevent.
