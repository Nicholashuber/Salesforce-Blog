# Data Cloud BigQuery integration: real-world sync patterns, identity resolution, and query architecture

Short answer: For most analytics teams, a hybrid approach works best — use Data Cloud's Streaming API + Pub/Sub + a lightweight Node/Heroku worker to stream high-velocity events into BigQuery for near-real-time dashboards, and scheduled bulk exports (Parquet → GCS → load jobs) for wide tables and historical backfills. Map Data Cloud's identity graph to a single stable primary key (export the Golden Record id / profile id) and store both raw event payloads and a normalized customer dimension for cohort queries.

## How do I choose streaming vs batch for Data Cloud BigQuery integration?

Streaming (Pub/Sub → BigQuery streaming inserts)

- Use streaming when dashboards require <1–5 minute freshness (real-time MRR, active sessions, or live eligibility checks). 
- Streaming avoids load-job latency and preserves event order if you add sequence keys, but it increases per-row ingestion costs and can complicate schema changes.

Batch (Data Cloud export → GCS → BigQuery load jobs)

- Use batch for wide, slowly changing datasets (360° profiles, flattened transaction history) and for large historical backfills. 
- Batch is cheaper per byte, supports Parquet/Avro, and is easier to evolve schema using partitioned, date-sharded tables.

Hybrid pattern (recommended)

- Stream events (page views, transactions, subscription events) into a narrow events table. Run nightly batch jobs that produce a denormalized customer table for heavy analytic joins and model training.

## How should I map Data Cloud identity to BigQuery (identity resolution)?

1. Export the resolved identity key. In Data Cloud, the Identity Resolution model produces a Golden Record id (export as profileId or goldenRecordId). Use that as the canonical primary key in BigQuery.
2. Store raw identifiers too. Keep arrays/columns for email_hash, phone_hash, external_id, and Salesforce Contact/Lead/Account IDs to trace back to source systems.
3. Maintain an identity mapping table in BigQuery:

```sql
-- canonical_customer dimension
CREATE TABLE analytics.canonical_customer (
  profile_id STRING NOT NULL,
  first_seen TIMESTAMP,
  last_seen TIMESTAMP,
  latest_email STRING,
  sf_contact_id STRING,
  source_ids ARRAY<STRING>,
  PRIMARY KEY(profile_id)
);
```

4. When streaming, include the profile_id on every event so joins to the canonical_customer table are simple and fast.

## How to build a deployable streaming pipeline (Streaming API + Pub/Sub + Node example)

High-level flow: Data Cloud Streaming API → Google Pub/Sub topic → Node/Heroku subscriber → BigQuery inserts.

Data Cloud configuration (UI breadcrumbs)

- Setup Data Cloud export: Data Cloud console → Data Pipelines → Streaming exports → New streaming export → Destination: Pub/Sub. Select dataset(s) and include the identity resolution field (profile_id / goldenRecordId) in the payload.

Node/Heroku subscriber example (minimal, production needs retries, batching, monitoring)

```javascript
// server.js
const {PubSub} = require('@google-cloud/pubsub');
const {BigQuery} = require('@google-cloud/bigquery');
const pubsub = new PubSub();
const bigquery = new BigQuery();
const subscriptionName = process.env.PUBSUB_SUBSCRIPTION;
const datasetId = 'analytics';
const tableId = 'events_stream';

const subscription = pubsub.subscription(subscriptionName);
subscription.on('message', async message => {
  message.ack();
  try {
    const payload = JSON.parse(message.data.toString());
    // normalize payload to match BigQuery schema
    const row = {
      profile_id: payload.profileId || null,
      event_type: payload.type,
      event_time: payload.timestamp,
      payload: payload // keep raw JSON for replay
    };
    await bigquery
      .dataset(datasetId)
      .table(tableId)
      .insert([row], {raw: true});
  } catch (err) {
    console.error('insert error', err);
    // implement DLQ / retry logic here
  }
});
```

Operational notes:

- Batch inserts (accumulate 100–10,000 rows) are more cost-efficient and avoid single-row throttling.
- Add a DLQ (Cloud Storage / Pub/Sub Dead Letter Topic) for failed messages.
- Expose Prometheus metrics on Heroku/Cloud Run for latency and error rates.

## What are incremental CDC patterns and how do I implement them?

Option A — Event-driven CDC (preferred for real-time):

- Use Data Cloud Streaming API change events. Each event contains operationType (insert/update/delete) and a timestamp. Maintain a high-watermark (lastProcessedTimestamp) in your worker state or a small control table in BigQuery and process only newer events.

Option B — Watermark-based batch CDC:

- Export only rows where lastModifiedDate > last_export_watermark. Store watermark in a control table and run routine load jobs.

Option C — Full snapshot + diff (for complex schema changes):

- Periodically export a full snapshot (Parquet) and run a merge in BigQuery:

```sql
MERGE analytics.canonical_customer T
USING staging.canonical_customer S
ON T.profile_id = S.profile_id
WHEN MATCHED THEN UPDATE SET T.latest_email = S.latest_email, T.last_seen = S.last_seen
WHEN NOT MATCHED THEN INSERT (profile_id, first_seen, last_seen, latest_email) VALUES (S.profile_id, S.first_seen, S.last_seen, S.latest_email);
```

## What query patterns should I use in BigQuery for MRR and churn cohorts?

MRR (monthly recurring revenue) by cohort (example assumes events table with profile_id, event_type, amount, event_time):

```sql
WITH invoices AS (
  SELECT
    profile_id,
    DATE_TRUNC(DATE(event_time), MONTH) AS month,
    SUM(amount) AS mrr
  FROM analytics.events
  WHERE event_type = 'invoice' AND amount IS NOT NULL
  GROUP BY profile_id, month
)
SELECT month, SUM(mrr) AS total_mrr
FROM invoices
GROUP BY month
ORDER BY month;
```

Churn cohort example (cohort by first paid month, churn if no invoice next 3 months):

```sql
WITH first_paid AS (
  SELECT profile_id, MIN(DATE_TRUNC(DATE(event_time), MONTH)) AS cohort_month
  FROM analytics.events
  WHERE event_type = 'invoice' AND amount > 0
  GROUP BY profile_id
),
payments AS (
  SELECT profile_id, DATE_TRUNC(DATE(event_time), MONTH) AS paid_month
  FROM analytics.events
  WHERE event_type = 'invoice'
)
SELECT
  f.cohort_month,
  p.paid_month,
  COUNT(DISTINCT p.profile_id) AS active_customers
FROM first_paid f
JOIN payments p USING(profile_id)
WHERE p.paid_month BETWEEN f.cohort_month AND DATE_ADD(f.cohort_month, INTERVAL 3 MONTH)
GROUP BY f.cohort_month, p.paid_month
ORDER BY f.cohort_month, p.paid_month;
```

If you run Snowflake and BigQuery in parallel, keep the canonical_customer table as the single source of truth and run the same SQL in each warehouse with minimal changes to data types.

## How should I estimate costs for a Data Cloud → BigQuery pipeline?

Estimate using a simple spreadsheet with these rows:

- Rows/day and average bytes/row (use sampled payloads from Data Cloud). 
- Streaming insert cost estimate = rows/day × bytes/row × streaming price factor (or per-MiB rate if you have it). 
- Batch load cost = storage for exported files (GCS) + load job bytes processed.
- Storage cost = active table size × months retained.
- Processing cost = Dataflow/Cloud Run or Heroku dyno runtime for transformation and CDC logic.

Choose streaming for low-latency needs and smaller throughput; choose batch for large throughput or when per-byte cost matters.

## Common mistakes (and how to fix them)

- **Exporting non-deterministic identifiers as primary keys.** Fix: export the Data Cloud Golden Record id / profile_id and use it as the canonical key in BigQuery.
- **Writing schema-changing events directly to a wide table.** Fix: write raw JSON events to a staging table and run nightly transforms to a stable schema.
- **No DLQ or retry strategy for streaming inserts.** Fix: implement DLQ (GCS or a Pub/Sub dead-letter topic) and exponential backoff retries.
- **Assuming streaming is always cheaper.** Fix: estimate per-byte streaming vs batch costs before choosing; batch loads often win on high-volume historical loads.
- **Not tracking watermarks for CDC.** Fix: store and atomically update last_processed_timestamp in a control table to guarantee idempotency.

## FAQ

### How do I stream Data Cloud to BigQuery?
Configure a Data Cloud streaming export to a Pub/Sub topic, subscribe with a worker (Cloud Run/Heroku) that normalizes events and does batched BigQuery inserts, and implement DLQ/retry.

### Should I use BigQuery streaming inserts or load jobs?
Use streaming inserts for real-time needs and small, frequent writes. Use load jobs (Parquet/Avro) for bulk historical loads and schema evolution — they are cheaper per byte.

### How do I keep Snowflake and BigQuery in sync?
Keep a single canonical export from Data Cloud (canonical_customer + raw events). Push the same files to both warehouses or centralize transformations in an ELT step so both warehouses read the same staged files.

### How do I include identity resolution in analytics queries?
Include the exported profile_id on every streamed and batch row so analytic joins use a stable canonical key rather than source-specific IDs.

### Can I use Cloud Dataflow or a managed connector instead of Node?
Yes. Dataflow offers autoscaling and native Pub/Sub connectors. The Node/Cloud Run approach is lower-cost and easier to iterate for small teams.

Mastering data at scale often starts with a small, observable pipeline: export the Data Cloud profile id, stream one event type into BigQuery, and build the first MRR dashboard. For a production roll-out, add batching, DLQ, and a scheduled full snapshot and merge.
