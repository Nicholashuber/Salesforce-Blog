# Data Cloud identity resolution: matching keys, golden records, and scale

Short answer: Design your Data Cloud identity resolution around a small, fast set of authoritative matching keys (external IDs, normalized email, E.164 phone), apply deterministic matching at ingest and probabilistic reconciliation in batch, and use explicit merge rules (source precedence, recency, completeness) to produce a versioned golden record you can audit. Test match rates with a representative sample and run an operational drift playbook (weekly metrics, manual review, threshold tuning).

## How should you choose primary matching keys for Data Cloud identity resolution?

Pick 2–4 complementary keys and rank them by trustworthiness. Typical choices:

- External system ID (CRM contact ID, marketing system ID) — deterministic, highest trust.
- Email (normalized) — high precision if you standardize and block on domain rules.
- Phone number (E.164) — good when validated; add country code normalization.
- Government ID / hashed SSN / customer loyalty ID — deterministic when available.

Practical rule: require an ingest-time deterministic key (externalId or hashed stable id) for immediate identity linking. Fall back to probabilistic keys (name+d.o.b+address) in nightly reconciliation.

## How to standardize and normalize matching keys before matching?

Normalization reduces false negatives. Standard transforms:

- Email: lowercase, trim, remove plus-tags for Gmail, canonicalize common domains.
- Phone: parse and store in E.164 using libphonenumber; drop extension into a separate field.
- Name: trim whitespace, remove diacritics, standardize common prefixes (Dr., Mr.).
- Address: USPS normalization for US addresses, uppercase canonical forms, parse street number vs unit.

Implement transforms in the ingest pipeline (Cloud Ingest transforms or an Edge processor). If you perform normalization in a pre-processing lambda or MuleSoft flow, persist both raw and normalized values in the transaction payload for auditability.

Example GraphQL ingest payload (simplified):

```graphql
mutation {
  upsertCustomer(input: {
    externalId: "crm-12345",
    rawEmail: "Jane.Doe+promo@Gmail.com",
    normalizedEmail: "jane.doe@gmail.com",
    rawPhone: "+1 (415) 555-1234",
    normalizedPhone: "+14155551234",
    firstName: "Jane",
    lastName: "Doe",
    rawAddress: "123 Main St Apt 4B, San Francisco, CA",
    normalizedAddress: "123 MAIN ST APT 4B, SAN FRANCISCO, CA 94105"
  }) {
    id
    status
  }
}
```

## How to design match rules, weights, thresholds, and staged matching?

Match rules fall into two buckets: deterministic and probabilistic.

Deterministic rules

- Exact externalId match.
- Exact hashed government ID.

Probabilistic (scoring) rules

- Build weighted attributes: email (0.35), phone (0.25), name (0.20), address (0.10), dob (0.10).
- Compute a composite score 0–100 and set two thresholds: accept (>= 85) and review (60–85).
- Use blocking keys to limit comparisons (e.g., same domain or same postal code) to reduce compute.

Sample matching-rule JSON (outline you can adapt to your Data Cloud match engine):

```json
{
  "name": "contact_probabilistic_v1",
  "weights": { "email": 35, "phone": 25, "name": 20, "address": 10, "dob": 10 },
  "thresholds": { "accept": 85, "review": 60 },
  "blockingKeys": ["normalizedEmailDomain", "postalCode"],
  "deterministicRules": [ { "type": "externalId" }, { "type": "hashedGovernmentId" } ]
}
```

Staged matching pattern

1. Ingest-time deterministic matching: upsert using externalId or hashed id for low-latency linking.
2. Nearline batch reconciliation (nightly or hourly): run probabilistic matching across recent deltas and historical groups to find new links and duplicates.
3. Manual review queue: surface records in the `review` band for human verification before automatic merges.

## How should you merge records and maintain golden-record confidence?

Define a transparent survivorship model. Common attributes:

- Source precedence: system A > system B > inbound feed.
- Recency: newer non-null values win when source precedence ties.
- Completeness score: prefer value sets that increase field coverage.
- Confidence cap: only auto-merge when composite score >= accept threshold.

Store merged results as a versioned golden record with provenance metadata: contributingIds, contributingSources, field-level source, mergeScore, mergeTimestamp, and mergeRuleId. Keep originals immutable and point golden records to the source IDs for replay.

Example golden-record field provenance structure (JSON snippet):

```json
{
  "goldenId": "golden-98765",
  "fields": {
    "email": { "value": "jane.doe@gmail.com", "source": "crm-12345", "confidence": 0.98 },
    "phone": { "value": "+14155551234", "source": "marketing-987", "confidence": 0.92 }
  },
  "contributingIds": ["crm-12345", "marketing-987"],
  "mergeScore": 90
}
```

## How do you scale matching and measure performance (match window, latency)?

Scale levers

- Blocking keys to prevent N^2 comparisons.
- Incremental matching on deltas instead of full-table pairwise runs.
- Shard by hash prefix or region for very large datasets.

Operational targets

- Ingest-time match latency: milliseconds to link by deterministic key.
- Batch reconciliation window: size and frequency trade accuracy for recency. For most orgs, nightly is a good starting point; high-throughput systems use hourly.
- Match throughput: validate with a pilot dataset. Plan capacity for peak daily ingest + nightly batch volume.

Monitoring metrics

- Match rate (percent of ingests linked automatically).
- Review rate (percent falling into review band).
- False positive rate (sampled and human-verified).
- Merge latency (time from detection to golden record update).

## How to test match rates and run a Trailhead-friendly experiment?

Experiment plan (one-day Trailhead / Developer org run):

1. Create a small dataset of 5k–10k synthetic contacts with controlled duplicates (20% duplicates with variations). Include externalId, rawEmail, phone, name, address.
2. Run normalization transforms via a simple Apex or Node script and persist normalized fields.
3. Ingest to Data Cloud using the GraphQL mutation above for each record.
4. Run your probabilistic match engine against the ingested set and record how many pairs score >= accept and >= review.
5. Sample 200 `accept` and 200 `review` matches and manually verify precision.
6. Adjust weights and thresholds until precision/recall hit your target (e.g., precision >= 98% in accept band).

You can script steps 2–4 with a small Node script calling the ingest API, or use an Apex batch in a connected org for smaller volumes. ## Common mistakes and how to avoid them

- **Relying only on raw emails or phones.** Normalize before matching; otherwise you undercount matches. Fix: add email and phone canonicalization in ingest.
- **Setting thresholds too low for auto-merge.** Low thresholds create false positives. Fix: use a review band and human-in-the-loop for borderline cases.
- **Merging without provenance.** Without source-level provenance you can't audit merges. Fix: store field-level source and contributingIds on every golden record.
- **Running full pairwise matches at scale.** Full N^2 runs will blow budgets. Fix: add blocking keys and incremental deltas.
- **Ignoring drift.** Match quality changes as data sources change. Fix: schedule weekly match-rate reviews and an automated sample audit.

## FAQ

### What is Data Cloud identity resolution?

Data Cloud identity resolution is the process of linking records that represent the same person or entity across systems, producing a single golden record and provenance metadata for each identity.

### Which matching keys should I make mandatory at ingest?

Make a deterministic external ID or a hashed stable identifier mandatory for immediate linking; normalize email and phone to improve automatic matches.

### Can identity resolution scale to 100M+ records?

Yes, but you must use blocking, sharding, and incremental reconciliation. Avoid full-table pairwise matching and plan nightly batch windows accordingly.

### How do I measure match quality in production?

Track match rate, review rate, sampled precision/recall, and false-positive counts. Store labelled review results to tune weights over time.

### How do I keep an audit trail for merged golden records?

Persist contributingIds, field-level source, mergeTimestamp, mergeRuleId, and a version history for each golden record so you can replay or roll back merges.
